1. 総括

結論: 文書の意味、画像編集、履歴、永続化、決定的再生の権威は、現状すでにRust Core側にあり、設計の核は成立しています。ただし、Win32から見た「単一のシステムコール表」は未完成です。値／IDだけのABI-v3プリミティブは79件中4件に限られ、大半は汎用C++クロージャと個別C ABIを通ります。また、Light Table swapはログを破棄する明示的例外です。したがって、Rust内部のcanonical journalは再生可能ですが、C++→Rust呼び出し列そのものは閉じた再生ログではありません。
78/79catalog primitive

canonical procedureとして再生可能。残る1件はsession-onlyのLight Table swapです。

4/79pointer-free public primitive opcode

ABI-v3の共通値／ID経路が公開しているprimitive数です。

3journal event kinds

Commit、HistoryMove、BranchCutに語彙が閉じています。

評価軸判定要約
画像編集・文書規則のRust所有適合C++側にraster編集、layer/plane規則、選択演算、Undo/Redo、native codecの別実装は見つかりません。
Win32のOS shell化概ね適合HWND、COM、dialog、clipboard、thread、DPI、Direct2D/D3DはWin32側です。
プリミティブの値／Rust-owned ID境界部分適合v3は適合しますが4 opcodeのみ。legacy mutationはC++ memoryのborrowed pointer/spanを同期コピーします。
canonical procedureと決定的replay強く適合Genesis、immutable Asset、procedure、pre/post digestからfresh Coreを再構築します。
Undo/Redoを含む非破壊履歴文書内は適合Undo/Redo/JumpはHistoryMoveとして記録され、Undo後の旧tailもbranchとして残ります。
すべての操作を含む完全なsession replay未適合New/Open/Recovery等のGenesis置換とLight Table swapは、文書journalの外側です。
「完全に非破壊」の正確な意味: 現状は、文書編集について「Genesis + immutable assets + canonical procedures + history eventsを正本とし、materialized documentやinverse deltaを派生cacheにする」という意味で非破壊です。RAM上の作業documentは更新され、session Genesisの明示置換もあります。純粋関数型の「メモリを一切上書きしない」設計や、アプリ操作全体のevent sourcingではありません。

4. C++ / Rustメモリ境界

現在の境界は、メモリ安全・寿命管理としては堅牢です。しかし、依頼で示された「primitive control planeはcall-by-valueまたはRust-owned ID/pointerのみ」という厳格な規則には、まだ全面適合していません。

経路現在の契約安全性厳格なprimitive原則
ABI-v3 primitive固定幅InkpodPrimitiveRequestV3を値copy。可変payloadはgeneration付きInkpodObjectId。良好適合
ABI-v3 bulk ingestcaller spanを検証し、復帰前にRust registryへdeep-copy。良好data-planeとして適合
legacy mutation APIC record、UTF-8、vector/span pointerをcall中だけborrowし、Rust owned値へ同期copy。契約上安全非適合
render snapshotRust-owned opaque pointer。Rendererが全経路でexactly-once release。良好許容されたRust pointer
CoreHost Adapter lanetokenの先にC++ callableを保存し、engine threadで任意C ABI callを実行。lifetime管理あり記録不能

適合しているv3 object registry

  • InkpodObjectIdはgeneration + object_type + valueで、wrong Core、stale、wrong typeを拒否します。
  • Rust側ObjectRegistryは単調増加ID、BTreeMap、4096 object、合計768 MiB等の上限を持ちます。
  • colors、stroke samples、rasterを先にRust-owned objectへ取り込み、primitive requestはIDのみを参照できます。
  • snapshot、thumbnail、export bytes、taskも同じgeneration-scoped modelで扱えます。

根拠: include/inkpod/core_ffi.h:966-1010, 5111-5259、rust/inkpod-ffi/src/abi/v3_records.rs:3-133、rust/inkpod-ffi/src/v3/mod.rs:60-206, 254-368

安全だが、目標境界ではないlegacy span

例えばstrokeはC++のsample spanをRust側でVec<StrokeSample>へ変換してからCoreへ渡します。call復帰後にpointerを保持せず、FFI panicもstatusへ封じ込めるため、現在の実装をmemory unsafeとは評価しません。ただし、そのcall recordだけを保存して後で再実行することはできないため、primitive syscallのcontrol planeとしては不適合です。

根拠: rust/inkpod-ffi/src/support/domain.rs:203-260、rust/inkpod-ffi/src/paint_history/paint.rs:479-518、rust/inkpod-ffi/src/support/boundary.rs:203-253

snapshot ownership

現行RendererはlegacyのInkpodSnapshot*を使いますが、これはRustが所有するimmutable objectへのopaque pointerであり、依頼の許容範囲です。SnapshotEnvelopeはsuccess、stale rejection、queue replacement/failure、surface close、shutdownの全経路で所有権をconsumeします。将来はmove-only RAII wrapperにするとmanual release事故をさらに減らせますが、設計逸脱ではありません。

根拠: apps/windows/renderer/renderer_host.h:65-74、apps/windows/app/core_host.cpp:956-1018、apps/windows/renderer/canvas.cpp:464-517, 2977-3027

CanonicalProcedureの永続record

永続fieldは固定幅値、stable ID、Rust-owned immutable AssetId、canonical bytes、digestです。caller pointer、外部path、frontend command ID、一時object IDを持ちません。decode後はtyped invocationを再構築し、再encodeが元のcanonical bytesと一致することも確認します。

実装は「意味上は一つ、物理的には二つ」のexecutor

PrimitiveRequest path

公開requestはSetMainLineColor、ReplacePalette、ApplyRasterStroke、ImportRasterAssetの4 variants。PrimitiveTransactionがworking CellDocumentとID cursorを持ち、一回のpublishでdocument、revision、history、journal、assets、cache、counterを更新します。

primitive/model.rs:328-386
primitive/executor.rs:38-174, 343-492

CanonicalInvocation path

広いfeature catalogはcrate-private typed invocationへ正規化し、Core全体をstaged cloneして既存feature methodを実行。exactly one revision/historyを確認後、procedureを作りstaged Coreをpublishします。

primitive/invocation.rs:19-318, 956-1684, 2077-2236

live実行とreplayは各primitive内では同じtyped invocation経路を共有し、どちらもcanonical journalへ到達します。そのため決定性の意味は成立しています。しかしtransaction/publish codeが二つあるため、「唯一のexecutor」という構造上の契約には未到達で、atomicity、ID予約、no-op、cache invalidationの将来driftと、Core全体cloneのコストが残ります。

Undo / Redo / branch

  • JournalEntryはCommit、HistoryMove、BranchCutだけです。
  • Undo、Redo、Jumpはdocumentを派生deltaで移動し、HistoryMove eventを追加します。
  • Undo後の新規commitはBranchCutを記録しますが、非activeな旧redo tailを消しません。
  • inverse/forward cacheを解放しても、Genesis + assets + journalから再構築できます。
  • no-op、invalid、cancel、staleはrevision、ID、history、journalを進めません。

根拠: rust/inkpod-core/src/journal.rs:63-255, 440-604, 617-883、rust/inkpod-core/src/history.rs:7-184, 321-359

再生保証の境界

保証されるもの: 同じreplay epoch、Genesis、immutable assets、journal event列から、同じCore document state digestとcanonical composite digestを得ること。現行goldenはfixed-point/int mathと複数effectを含めて検証しています。
保証されないもの: Win32 UI state、window配置、GPU cache、thread timing、外部path、OS codec状態を含むアプリsession全体。またNew/Open/Recovery/Sequence activation等のGenesis置換前の履歴は、置換後documentのjournalには残りません。

明示的例外: LightTableSwapWithActive

LightTableSwapWithActiveはstable primitive IDを持つ一方、catalog上replayable: falseです。実装はincoming/outgoing imageをflattenし、新しいCellDocumentを公開後にreset_history(true)を呼び、StateId、ProcedureId、journal、Genesisを再初期化します。これは今回提示された「すべてのprimitiveがログに入り、完全に非破壊」という定義と直接衝突します。

設計上は二択です。 (A) incoming/outgoing sourceをimmutable AssetIdで参照するreplayable procedureにして旧状態をbranchとして残す、または (B) primitive catalogから外し、Open/Replaceと同じdocument lifecycle / Genesis replacementとして明示的に分類するべきです。

根拠: rust/inkpod-core/src/primitive/catalog.rs:302-309、rust/inkpod-core/src/animation/light_table_operations.rs:682-769、rust/inkpod-core/src/core.rs:575-587、docs/file-format.md:97-99

DocumentId、CellId、LayerId、PlaneId、GuideId、Light Table、Vector、View、および意味別revisionはnewtype化されています。一方、ProjectId、CutId、FrameId、SequenceIdはまだありません。現行canonical hierarchyはstandalone Cell modelで、sequenceはdocument UUID + source generation + Vec indexを使います。

hardening上のデータ構造課題

  • Stable ID上限: 永続ID上限は0x7fff_ffff_ffff_ffffですが、StableIdCursor::take_rawはsaturating_addして無条件に値を返します。上限直前でchecked reservationし、失敗時にdocument/journal/IDを全く進めない契約とtestが必要です。
  • Snapshot delta: RenderSnapshotはrevision付きtileを持ちますが、明示的なdirty rect、removed tile、invalidation spanを持ちません。Rendererはsnapshot比較から推論します。Core snapshot contractに合わせるならbounded delta metadataが必要です。
  • Core clone: CanonicalInvocation pathはCore全体をcloneしてpublishします。tile/assetsはArc/COWですが、長いhistory/journalとmetadata vectorのclone costは増えます。
  • 非有限zoom: ZoomFactor::clampedはNaNを拒否する一方、±Infinityを上下限へclampします。非有限値拒否という不変条件へ揃える余地があります。

8. 推奨する目標構造と移行順序

Phase 0 — replay境界を用語として固定

  1. Document primitiveは必ずcanonical procedureとなり、成功commitだけがjournalへ入る。
  2. History moveはUndo/Redo/Jumpで、同じjournalに入る。
  3. Session / Genesis replacementはprimitiveではない、と明示する。全session replayが必要なら別の上位journalを導入する。
  4. Light Table swapをdocument primitiveとして残すか、session replacementへ再分類するかを先に決める。

Phase 1 — C++の権威cacheを解消

  1. stable LayerIdでadjustment metadata/parametersを取得するbounded Rust queryまたはpresentation snapshotをC ABIへ追加。
  2. Open、Undo/Redo/Jump、document replacement、revision change後にCoreからUI projectionを再構築。
  3. EffectsUiState::adjustmentsは削除するか、session/generation/document revision/digestに束縛された純粋cacheにする。

Phase 2 — 全mutationを一つのvalue/ID syscall表へ

PrimitiveCallVn {
  struct_size, abi_version,
  primitive_id, primitive_schema_version,
  replay_epoch, base_document_revision,
  target_ids[], fixed_arguments,
  rust_object_ids[], asset_ids[]
}

PrimitiveResultVn {
  result_class, committed_revision,
  procedure_id, committed_state_id,
  primitive_id, schema_version
}
  1. catalogをschema、Rust enum、C opcode、decode、route inventoryの単一正本にする。
  2. 可変長colors/samples/points/raster/textは、mutation前にbounded ingestし、Rust-owned generation IDまたはpersistent AssetIdへ変換。
  3. Win32 controllerからmutation-capableな汎用CoreOperationを段階的に除去。query、OS I/O、lifecycleだけを別typed laneに残す。
  4. CoreHost completionでprocedure_id、state_id、opcode/schema、queue sequenceを受け取り、Rust journalと相関可能にする。pathやpixel payloadはlogしない。

Phase 3 — Rust executorを一つに収束

  1. 全replayable primitiveをclosed typed command envelopeへ昇格。
  2. 一つのtransaction publisherでbase revision、working state、ID reservation、no-op、post digest、history、journal、cache invalidationを扱う。
  3. feature methodはtransaction上の純粋なapply kernelとし、Core全体clone-and-replaceをやめる。
  4. Stable IDは必要個数をcommit前にchecked reserveし、overflow時はall-or-nothing failure。

Phase 4 — 証明可能な受入条件

  • 全78 replayable primitiveに、成功、no-op/invalid、fresh replay、save/openのconformance vectorを1つ以上持つ。
  • 全Win32 document mutation commandが、実行時に「0または1件のcanonical procedure」へ対応することをinstrumentationで検証。
  • 同じGenesis/assets/journalから、state digestとcanonical composite digestが一致。
  • C ABI mutation recordにpointer、path、callback、frontend command IDがないことをheader/Rust layout両方で生成検査。
  • UI projection cacheはsession/generation/revision一致を必須とし、stale targetを別documentへ再解決しない。
  • Project/Cut/Frame/Sequenceを導入する時点でstable ID namespaceとfile/replay versionを同時更新。

最終評価: Inkpodの「文書編集エンジン」はすでにRust Core中心で、canonical procedure、asset、journal、branch、fresh replayによる非破壊モデルは実装上の強みです。次に必要なのは機能をC++からRustへ移すことではなく、すでにRustにある機能への入口を、全件共通の値／Rust-owned ID primitive tableへ収束させることです。同時にLight Table swapの位置付けと、調整レイヤーUI cacheの権威性を解消すれば、提示された設計原則と実装の差は大きく縮まります。
